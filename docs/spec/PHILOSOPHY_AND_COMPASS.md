# 🧭 ForgeFlow 엔지니어링 철학 및 적응형 거버넌스 헌장 (Engineering Compass)

> **"사용자의 근본 문제를 100% 해결하되, 배보다 배꼽이 더 큰 형식적 오버엔지니어링을 철저히 배제한다."**  
> 본 문서는 ForgeFlow 프레임워크와 에이전트 시스템을 설계·구현·고도화할 때 언제나 올바른 방향으로 나아가고 있는지 점검하는 **최상위 엔지니어링 나침반(Compass)**입니다.

---

## 1. 북극성: 요구사항의 본질과 목적 완결성 (The North Star)

### 1.1 표면적 요구(Demand)와 근본 문제(JTBD)의 엄격한 분리
- **관측된 현상(Incident)에서 출발**: 사용자가 겪고 있는 병목이나 시스템의 관측된 결함 데이터를 정확히 측정하고 기록합니다.
- **표면적 솔루션 선호(Stated Demand)에 매몰 금지**: 사용자가 "A 기능을 만들어 달라"고 요청했을 때, 그것을 그대로 복제하는 것은 하책입니다. 사용자가 왜 그것을 원했는지 5-Whys를 통해 파고들어 시스템 내부의 근본 제약(Root Cause)을 규명해야 합니다.
- **본질적 과업(Job-To-Be-Done, JTBD)의 정의**: 시스템이 최종적으로 달성하고 보장해야 하는 상태 전이(State Transition)와 가치를 한 문장으로 명확히 정의합니다.

### 1.2 일반론적 평균값 타협의 배제
- 인터넷이나 일반적인 템플릿에 흔히 나오는 "좋은 말들의 합집합"이나 평균값 요약으로 설계서를 채우지 않습니다.
- 실제 구현 현장에서 모호함 없이 단번에 100% 목적을 달성할 수 있는 구체적인 불변식(Invariants), 도메인 경계, 입출력 계약만을 담습니다.

## 2. 오버엔지니어링 경계와 실용적 검증 (Pragmatic Rigor vs. Brittle Ceremony)

### 2.1 취약한 검증(Brittle Testing)의 함정 경계
- **문제 인식**: 사소한 JSON 키 정렬 차이, 공백 하나, 타임스탬프 형식, 미세한 표준 출력(stdout) 문자열 차이로 인해 정상 동작하는 시스템이 무조건 실패(Fail) 처리되는 패턴은 진정한 신뢰성이 아니라 시스템을 경직되게 만드는 **취약한 오버엔지니어링(Brittle Testing)**입니다.
- **불변식 중심의 실용적 오라클**:
  - 문자열 전체 비교 대신 시스템의 **핵심 상태 불변식(Safety Invariant)**을 어설션합니다.
  - 가역적 출력이나 포맷의 유연성은 허용하되, 데이터의 무결성과 상태 전이의 방향성은 엄격히 통제합니다.

### 2.2 실전 중심의 2대 검증 오라클 (Pragmatic Oracles)
1. **인시던트 적합성 (Incident-Fit)**:
   - 가상의 이론적 시나리오가 아니라, 실제 보고되거나 발생 가능한 실패 패턴을 재현하는 골든 픽스처(Fixture)를 준비하고, 해당 결함이 확실히 해소되었음을 입증합니다.
2. **설치 배포 전달성 (Consumer Delivery Readiness)**:
   - 개발 환경이나 격리된 테스트 하네스에서만 돌아가는 코드가 아니라, 실제 최종 사용자에게 전달/설치된 엔트리포인트(CLI 바이너리, 모듈)에서 비파괴적 프로브(Probe, 예: `--help`, 버전 질의 등)를 실행하여 런타임 전달성을 증명합니다.

## 3. 적응형·비례적 거버넌스 (Adaptive & Proportional Governance)

### 3.1 과업 볼륨에 비례하는 유연성 (Proportionality)
- **배보다 배꼽이 더 큰 관료주의 타파**: 실행 파일 하나를 수정하거나, 소규모 버그를 고치거나, 국소적인 설정을 변경하는 작업에 풀스펙의 10대 항목 설계서와 3인 패널 심사를 강제하는 것은 심각한 낭비입니다.
- **과업의 볼륨과 목적에 따른 유연한 처리**:
  - 변경의 성격과 리스크에 맞게 문서 요구조건과 검증 흐름을 유연하게 완화할 수 있어야 합니다.
  - 꼭 필요한 시점에 엔지니어링 측면을 더 깊이 따지는 실용적 점진주의를 채택합니다.

### 3.2 작게 시작하여 점진적으로 확장하는 전략 (Gradual Escalation)
- **Start Lean**: 처음부터 모든 것을 포괄하는 거대한 티어로 시작하지 않고, 가장 작고 가벼운 범위에서 핵심을 정의합니다.
- **에스컬레이션 트리거**: 구현이나 검증 과정에서 숨겨진 아키텍처 결합, 보안 경계 침범, 비가역적 파괴가 발견될 때만 티어를 한 단계씩 높여 심사를 확장합니다.

### 3.3 양방향 문(Type 2) vs 일방향 문(Type 1) 결정 원칙
- **Type 2 (가역적 결정 / Two-Way Door)**:
  - 실패해도 쉽게 롤백 가능하거나 파급력이 국소적인 변경(문구 수정, 내부 리팩토링, 성능 튜닝 등).
  - 경량화된 변경 노트(CHANGE_NOTE)와 핵심 검증으로 신속히 전진합니다.
- **Type 1 (비가역적 결정 / One-Way Door)**:
  - 시스템의 코어 아키텍처, 공용 API 인터페이스, 보안/권한 통제, 영속 데이터 마이그레이션 등 되돌리기 극히 어려운 변경.
  - 엄격한 사전 심사, 상태 전이표, 다중 심사관 승인을 거쳐 결함을 원천 차단합니다.

## 4. 자가 점검 나침반: 5대 질문 (The Self-Check Compass)

에이전트와 엔지니어는 기획, 설계, 검증의 모든 단계에서 다음 5가지 질문을 스스로에게 던져야 합니다:

```text
┌────────────────────────────────────────────────────────────────────────┐
│                      🧭 5대 자가 점검 체크리스트                       │
├────────────────────────────────────────────────────────────────────────┤
│ 1. [본질 파악] 사용자의 표면적 요구(Demand) 뒤에 숨은 진짜 해결 과업    │
│    (JTBD)을 명확히 정의했는가?                                         │
│                                                                        │
│ 2. [오버엔지니어링 경계] 지금 작업의 크기(Volume)에 비해 설계서나     │
│    검증 절차가 과도하게 무겁지 않은가? (배보다 배꼽이 크지 않은가?)    │
│                                                                        │
│ 3. [실용적 검증] 사소한 포맷/출력 차이에 깨지는 취약한 테스트인가,     │
│    본질적 불변식과 런타임 전달성을 보장하는 실용적 오라클인가?         │
│                                                                        │
│ 4. [점진적 확장] 작게 시작하여 필요할 때 티어를 올릴 수 있도록 유연한   │
│    경로를 마련해 두었는가?                                             │
│                                                                        │
│ 5. [목적 완결성] 평균값의 타협이 아닌, 실제로 의도한 목적을 결함 없이  │
│    100% 달성하고 있는가?                                               │
└────────────────────────────────────────────────────────────────────────┘
```
